### A rate-limit failure, and why it is not in the table above

The first execution of this pass returned `llm_step_error_rate` **0.037** —
`ZL-022` failed with a Groq 429 on tokens-per-minute (limit 8000, used 6917,
requested 1109, "try again in 195ms"). The route still matched; the call
simply never happened, so `valid_structured_output` scored 0.0 for a reason
that has nothing to do with the model.

`MAX_CONCURRENCY = 2` spends a per-minute token budget faster than the Groq
SDK's default retries absorb it. Re-run serially, the same pass returns
0.000 with all five scorers at 1.000, which is the run recorded above.

Recorded here rather than quietly discarded, because it is a real property of
how this suite is executed and it will recur: **the TPM ceiling, not the daily
request quota, is what this suite runs into first.** Stage 1 raises per-call
token counts by roughly 25x, which makes this the constraint to watch.

### Retrieval was not the problem in this run

Clause retrieval **worked**. It returned real, correctly-parsed clauses on
every case — 7.4/10.1/11.1, 3.4/5.9, 6.6/15.3. The model was shown clauses
and abstained anyway.

Four of the five abstentions give the same reason, in the model's own words:

> "No changed fields were supplied in the register (the before→after map is
> empty), and none of the provided clauses address a change because there is
> nothing to change."

> "There are no changed fields in the register (the before→after mapping is
> empty), so none of the provided clauses (6.6 and 15.3) can govern a
> non-existent change."

### Why this happens, and what it confirms

`llm/ground.py`'s `build_prompt` renders `changed_fields` and then instructs
the model to decide "using only the clauses above". For an uncovered case
`changed_fields` is `{}` **by definition** — the not-covered route is
*precisely* the route where all five watched fields are identical.

So the model is handed an empty diff, asked what changed, and told to answer
only from the clauses. It correctly refuses to reason about a change it was
never shown. The abstentions are not model failures; they are the model
being right about the question it was actually asked.

Meanwhile `status: F → V` — *Forslag* → *Vedtaget*, the plan formally
adopted, the actual explanation for GR-002 and GR-004 — sits in the record
and is withheld from it.

**This is [improvement 5](../improvements.md) measured rather than argued**,
and it is a stronger result than that document claims. Improvement 4 predicts
retrieval failing silently and the model abstaining on a question it never
saw; here retrieval succeeded and the model *still* abstained, because the
diff it was given was empty. Sending the whole document (improvement 4) would
not on its own have fixed this run. Sending the whole record (improvement 5)
is the change that addresses it.

It also confirms the plan's decision to do improvements 4, 5 and 6 as one
change rather than three: fixing either half alone leaves the model answering
a question that still does not make sense.

## What this run does not measure

Same scope as the three previous baselines — see `baseline-2026-08-22.md`'s
"What this does not measure" for the full list. Four notes specific to this
document:

- **The offline suite does not score grounding at all.** `load_all_cases()`
  is the 35 real plus 5 synthetic cases; golden set v2
  (`grounding_cases.jsonl`, GR-001…005) is not in it. The prose scorers above
  measure `assess` and `summarise`, never the autonomous decision. That is
  [improvement 2](../improvements.md), and it is stage 2 of the plan.
- **The grounding rate above is n=5**, one pass, on five real documents. It is
  a floor to compare against, not a precise rate.
- **Three of the five documents' text extraction is lossy.** pypdf warns
  repeatedly about CFF Type1 font encodings without fontTools installed. This
  did not cause the abstentions in this run — the clauses parsed — but it is
  a known source of quote-verbatim failure and is why `clause_is_verbatim`'s
  committed threshold is 0.95 rather than 1.000.
- **`tests/test_demo_seed_reset.py::test_seed_reset_seed_is_repeatable` is
  flaky** and failed during this session's suite run (342 of 343 passed). It
  asserts `first == second` across two live seeded runs, i.e. exact
  reproducibility of a model call; it flaked between `escalated` and
  `grounded_ignore`. Pre-existing, not caused by anything here, and a test
  design issue rather than a regression: `temperature=0` is not a determinism
  guarantee on a hosted MoE endpoint (`baseline-2026-08-22.md`'s `ZL-018`
  finding).
