## Precondition: rule engine coverage (GATE, not the achievement)

**1.000** (34/34). `apply_rules` reproduces every golden label and rule

`tests/test_rules_engine.py`, which is part of the normal test suite, not

## The one failure, in full

**`ZL-018`** (file, R1, permitted use `Boligområde` → `Område til
offentlige formål`, Tårnby): in this pass, the model's summary did not
include the source doklink
(`https://dokument.plandata.dk/20_1071769_1690462796590.pdf`) verbatim.
`citation_fidelity` is the most important scorer this suite has - it is the
project's one rule ("every autonomous decision must be traceable to the
source that justified it"), tested mechanically - so this is the single
most significant finding in this baseline, not a rounding error to wave
past.

Re-running the same case (see Stability, below) shows this is
**intermittent, not systematic**: the same case cited its source correctly
in one of the three stability passes. `temperature=0` is not a determinism
guarantee on a hosted MoE endpoint (Groq's `openai/gpt-oss-120b`), which is
exactly what this looks like.

## Stability (`--stability 3`, recorded but not gated)

Three full local passes (`--no-langfuse`), same 39 cases, same code:

| Pass | `citation_fidelity` | Failing case ids | LLM error rate | Cost |
|---|---|---|---|---|
| 1 | 1.000 | — | 0.000 | $0.004875 |
| 2 | 0.952 | `ZL-018` | 0.000 | $0.004797 |
| 3 | 0.905 | `ZL-004`, `ZL-018` | 0.000 | $0.004597 |

Every other scorer (`no_invented_numbers`, `states_both_values`,
`did_not_read_the_document`, `valid_structured_output`, route match) scored
1.000 across all three passes, with zero LLM-step errors in every pass.
`citation_fidelity` is the only scorer that moved, and it moved by exactly
one failure category: the model omitting the doklink from its summary.
`ZL-018` failed 2 of 3 passes; `ZL-004` failed 1 of 3.

**Not gated deliberately** (see `evals/README.md`): three passes on a hosted
endpoint is a sample, not a determinism proof, and gating CI on a number
this small could produce an intermittently-red build - which teaches people
to ignore red builds, the opposite of what a gate is for. This stability
range (90.5%-100% on `citation_fidelity`) is the honest starting point
Phase 5's thresholds should be derived from, once more runs accumulate.

## What this run also found (a free-tier operating constraint)

A pre-fix run of the full 39 cases at `MAX_CONCURRENCY=4` and no retry hit
Groq's published 8,000 TPM rate limit on the free tier 3 times out of 21
calls (all `429 rate_limit_exceeded`), because concurrent eval calls at
~600-1000 tokens each can burst past that ceiling within a minute. Fixed by
lowering `evals/run_baseline.py`'s `MAX_CONCURRENCY` to 2 and adding a
rate-limit-aware retry in `evals/tasks.py` (`_with_rate_limit_retry`, which
sleeps for the delay Groq's own error body states). The primary run and all
three stability passes above ran after that fix, with zero errors. Recorded
here because it is a real, load-bearing property of the free tier this
project runs on (see `CLAUDE.md`'s stack table on the 1,000 requests/day
budget) - Phase 5's CI gate will need to account for it, not rediscover it.

## What this does not measure

- **Whether an escalation was worth a person's attention.** No
  `escalation-derived` cases exist yet - Phase 3's review queue is what
  produces them. The 12 real `escalate` cases and 5 synthetic
  `not_covered` cases test whether the agent escalates *correctly per the
  rule set*, not whether a human reviewer found the escalation useful.
- **Retrieval quality.** No retrieval exists in this system yet - the agent
  never opens the source plan document.
- **Regression over time.** This is one snapshot. Nothing gates a pull
  request against it yet - that is Phase 5, and this baseline (plus at
  least one more recorded run) is what its thresholds get derived from,
  rather than picking numbers out of the air now.
- **The synthetic NOT_COVERED cases' representativeness.** All 5 are
  zone-status-alone transitions, hand-constructed from real source records.
  They exercise `assess()`'s structured output and citation discipline, but
  they cannot speak to what real NOT_COVERED cases in the wild look like -
  see `evals/golden/README.md` on why this set is temporary.
- **Escalate/ignore case correctness beyond routing.** These 18 cases never
  call the model, so nothing here scores prose quality for them - only that
  `apply_rules` routed them correctly (folded into the rule-engine
  precondition above).
